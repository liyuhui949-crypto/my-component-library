## 二、Vue 技术深度（核心考察）

### 4. Vue3 的 Proxy 响应式和 Vue2 的 defineProperty 具体有什么区别？ ⚠️

**考察点：** 是否真的理解原理，而不是背八股

**回答模板：**
> **数据劫持方式不同：**
> - Vue2 用 `Object.defineProperty` 递归遍历对象所有属性，对每个属性重写 getter/setter。问题是：1）无法检测新增/删除属性，需要 `Vue.set`/`Vue.delete`；2）无法监听数组下标变化，所以 Vue2 重写了 7 个数组方法；3）初始化时需要递归遍历整个对象，深层嵌套有性能开销。
> - Vue3 用 `Proxy` 代理整个对象，不需要递归遍历初始化，访问到嵌套对象时才递归代理（惰性递归）。能天然拦截新增/删除属性、数组下标操作，不再需要 hack。
>
> **依赖收集不同：**
> - Vue2 每个属性一个 Dep 实例，收集依赖的是 Watcher。
> - Vue3 用 `WeakMap + Map + Set` 三级结构：`WeakMap<target, Map<key, Set<effect>>>`，依赖收集更精细。
>
> **实际影响：** Vue3 在大数据量对象初始化时性能明显更好，因为是惰性代理。Vue2 在深层嵌套对象场景下初始化卡顿明显。

**加分点：** 如果能说出"Vue3 的 reactive 用 Proxy，ref 用的是 .value 的 getter/setter 触发依赖收集"，会非常加分。

### 5. Composition API 和 Options API 本质区别是什么？你怎么做选型？ ⚠️

**考察点：** 技术判断力

**回答模板：**
> **本质区别：** Options API 按选项（data/methods/computed）组织代码，同一个逻辑的代码分散在不同选项里；Composition API 按逻辑关注点组织代码，一个功能的相关逻辑写在一起。
>
> **我的选型经验：**
> - 小型组件、逻辑简单的页面：Options API 就够了，更直观
> - 复杂组件、多个功能混杂的页面：Composition API + composables 抽离，可维护性好很多
> - 实际项目中我倾向于用 Composition API，但不是为了"新"，而是因为复杂业务里逻辑复用（useXxx）比 mixins 更可控——mixins 有命名冲突和来源不清晰的问题
>
> **迁移实践：** 我在欣悦的项目里做过 Vue2 → Vue3 迁移，Options API 和 Composition API 是可以混用的，Vue3 兼容两种写法，所以可以渐进式迁移，不需要一次性重写。

### 6. Vue 的 nextTick 是做什么的？实现原理是什么？

**考察点：** 对 Vue 异步更新机制的理解

**回答模板：**
> Vue 的 DOM 更新是异步的——数据变化后不会立即更新 DOM，而是把更新推入一个微任务队列，同一个 tick 内的多次数据变化会合并成一次 DOM 更新。`nextTick` 就是在这次 DOM 更新完成后执行回调。
>
> **实现原理：** 本质就是包装一个微任务（Promise.then），把回调推到微任务队列末尾。Vue2 里为了兼容性依次降级：Promise → MutationObserver → setImmediate → setTimeout。Vue3 直接用 `Promise.then`，不再考虑兼容。
>
> **使用场景：** 数据更新后需要操作最新的 DOM，比如获取元素尺寸、聚焦输入框。

---

### 7. Vuex 和 Pinia 有什么区别？你为什么用 Pinia？

**考察点：** 技术选型能力

**回答模板：**
> **核心区别：**
> - Pinia 去掉了 Mutation，只有 State + Getters + Actions，更简洁
> - Pinia 完全支持 TypeScript 类型推导，Vuex 的 TS 支持比较弱
> - Pinia 不需要嵌套模块，每个 store 独立，按需引入，天然支持 tree-shaking
> - Pinia 的 API 和 Composition API 风格一致，写起来更自然
>
> **我的选择：** 新项目用 Pinia，老项目维护用 Vuex。实际上 Pinia 就是 Vuex 5，Vue 官方已经推荐 Pinia 作为默认状态管理方案。

### 8. 你们欣悦的项目里，移动端用 Vue2、后台用 Vue3，为什么同一个项目两种技术栈？ ⚠️

**考察点：** 技术决策能力、是否理解迁移成本

**回答模板：**
> 移动端是已有的 Vue2 项目，已经跑了两年多，业务逻辑复杂、历史包袱重。如果要迁移到 Vue3，需要同时改 Vant（Vue2 版）到 Vant 4、Vuex 到 Pinia、处理 breaking change，测试成本很高，而项目一直在迭代，没有合适的窗口期做迁移。
>
> 后台管理系统是新建的项目，没有历史包袱，直接选了 Vue3 + Composition API + Element Plus。
>
> **我的判断：** 老项目迁不迁移取决于 ROI。如果业务稳定、没有新需求驱动，迁移的收益主要是开发体验，但风险是引入 regression bug。新项目直接用 Vue3 是确定性的收益。所以"同项目两种技术栈"不是设计缺陷，是务实的工程决策。

**要点：** 面试官问这个问题不是质疑你，是看你有没有"技术迁移的成本意识"。不要说"领导不让迁"，要说清楚你自己评估过 ROI。

## 三、性能优化（高频追问）

### 9. 你说首屏从 4s 优化到 1.5s，具体怎么排查的？ ⚠️

**考察点：** 是真做过还是背的优化清单

**回答模板：**
> **排查过程：**
> 1. 先用 Lighthouse 跑一次评分，看到 LCP 4s，Performance 面板里看到首屏加载了 1.2MB 的 JS bundle
> 2. 在 Network 面板按 Size 排序，发现一个 vendor.js 800KB，包含了 ECharts 全量引入、Element Plus 全量引入
> 3. 首屏实际只用到了路由首页和导航组件，但所有页面的代码都打在一个 bundle 里，没有做路由级别的 code splitting
>
> **优化措施：**
> 1. **路由懒加载**：`() => import('./views/xxx')`，首屏只加载当前路由的代码
> 2. **组件异步加载**：`defineAsyncComponent` 加载非首屏组件
> 3. **按需引入**：ECharts 按需引入需要的图表类型，Element Plus 用 unplugin-vue-components 自动按需导入
> 4. **图片懒加载**：首屏以下的图片用 `loading="lazy"` + Intersection Observer
> 5. **开启 Gzip**：Nginx 配置 gzip 压缩，bundle 从 1.2MB 降到约 400KB
>
> **结果：** LCP 从 4s 降到 1.5s，Lighthouse 性能评分从 45 提升到 85。

**要点：** 关键是展示**排查过程**，不是直接报答案。面试官想看的是"你怎么定位问题"，不是"你知道哪些优化手段"。

### 10. 虚拟滚动怎么实现的？为什么 FPS 从 12 提升到 58？ ⚠️

**考察点：** 是否真的理解虚拟滚动原理

**回答模板：**
> **问题背景：** 后台管理系统的数据表格，后端一次返回万级数据，前端直接用 Element Plus 的 el-table 渲染，滚动时严重卡顿。
>
> **排查：** Chrome DevTools 的 Performance 面板录制滚动过程，发现每帧的 Recalculate Style + Layout 耗时 80ms+，原因是 DOM 节点过多（万级 tr），每次滚动触发大量重排重绘。
>
> **方案：**
> 1. 基于 vue-virtual-scroller 二次封装，核心原理是：只渲染可视区域的 DOM 行（约 20-30 行），通过 `transform: translateY` 模拟滚动位置
> 2. 监听滚动事件，计算当前可视区域的起始索引，动态替换渲染的数据
> 3. 每行高度固定，通过 `总高度 = 行数 × 行高` 撑起滚动条
>
> **FPS 提升原因：** DOM 节点从万级降到稳定 50 个左右（可视区域 + 上下缓冲区），每帧的 Layout 计算量大幅减少。
>
> **踩坑：** 如果行高不固定，需要额外的动态高度测量逻辑，会复杂很多。我们的场景行高是固定的，所以方案相对简单。

### 11. Electron 内存泄漏是怎么排查的？ ⚠️

**考察点：** 问题定位能力

**回答模板：**
> **现象：** "微联"应用使用一段时间后内存持续增长，从 200MB 涨到 1GB+，切换页面后内存不释放。
>
> **排查过程：**
> 1. 打开 Chromium DevTools 的 Memory 面板，拍一个 Heap Snapshot
> 2. 操作一段时间后再拍一个，对比两个 Snapshot，看哪些对象在增长
> 3. 发现两类问题：
>    - **事件监听未清理：** 每次进入聊天页面都会注册 `ipcRenderer.on` 监听，但离开时没有 `removeListener`，导致回调函数和它引用的上下文都无法被 GC
>    - **定时器未清理：** 消息轮询的 `setInterval` 在组件销毁时没有 `clearInterval`
>
> **修复：**
> 1. 封装了 `useIpcListener` composable，在 `onUnmounted` 里自动清理监听
> 2. 全局排查所有 `setInterval`/`setTimeout`，确保在组件销毁时清除
> 3. 主进程侧加了内存使用监控，超过阈值主动触发 GC
>
> **结果：** 长时间使用内存稳定在 300MB 左右，不再持续增长。

## 四、工程能力

### 12. 你封装组件时怎么设计 API？怎么决定 props 和 slots？ ⚠️

**考察点：** 组件设计思维

**回答模板：**
> **我的设计原则：**
> 1. **props 放配置型数据**——控制组件行为和展示的参数，比如 `size`、`disabled`、`dataSource`
> 2. **slots 放不确定的 UI**——需要自定义渲染的部分，比如列表项的渲染、操作按钮区域
> 3. **events 放行为通知**——组件内部发生了什么，通知父组件，比如 `@change`、`@submit`
>
> **实际案例：** 我封装的流程卡片组件，业务需求是两省工作台都要用，但卡片里的操作按钮不同：
> - `title`、`status`、`data` → props，因为是数据驱动
> - 操作区域 → 具名 slot `#actions`，因为两省的操作按钮不一样
> - `@approve`、`@reject` → events，因为父组件需要响应
>
> **反面教训：** 早期我封装组件喜欢用大量的 props 来控制渲染，结果组件越来越臃肿，一个组件 20+ 个 props。后来学到"如果一个区域的渲染逻辑超过 3 种可能，就应该用 slot 而不是 prop"。

### 13. 两省工作台复用同一套组件库，遇到需求差异怎么处理？

**考察点：** 实际工程取舍

**回答模板：**
> **策略是"80% 共用 + 20% 可定制"：**
>
> 1. **通用逻辑抽到组件内部**——比如流程卡片的状态流转、数据看板的布局结构，这些两省是一样的
> 2. **差异部分通过 props 配置**——比如河南省的工单有"转商机"流程，海南省没有，通过 `showConvertLead: boolean` 控制
> 3. **完全不同的部分用 slot 覆盖**——比如两省的操作按钮区域完全不同，用具名 slot 让各省自己传
> 4. **实在无法共用的就独立写**——不要为了"复用"强行抽象，有些页面业务逻辑完全不同，硬塞进一个组件反而更难维护
>
> **实际经验：** 15 个组件里，有 12 个是完全共用的（通过 props/slot 适配差异），有 3 个差异太大，最终是独立写的。复用率约 80%，但开发效率提升确实很明显——第二个省的开发周期比第一个省缩短了将近一半。

## 五、跨端开发

### 16. Electron 主进程和渲染进程怎么通信的？

**考察点：** Electron 架构理解

**回答模板：**
> **三种方式：**
> 1. **ipcMain / ipcRenderer**：最常用。渲染进程 `ipcRenderer.send('channel', data)` 发消息，主进程 `ipcMain.on('channel', handler)` 接收。主进程回复用 `event.reply` 或 `event.returnValue`。
> 2. **invoke / handle**：推荐的异步方式。渲染进程 `ipcRenderer.invoke('channel', data)` 返回 Promise，主进程 `ipcMain.handle('channel', handler)` 处理并返回结果。比 send/on 更优雅，有错误处理。
> 3. **remote 模块**：已废弃，不推荐。
>
> **我们项目的实践：** 大部分通信用 `invoke/handle`，比如文件操作、系统通知。即时通讯的消息推送用 `send/on`，因为是主进程主动推给渲染进程的单向通信。

### 17. UniApp 多端适配遇到过什么坑？

**考察点：** 跨端实战经验

**回答模板：**
> **主要的坑：**
> 1. **CSS 兼容性**：支付宝小程序不支持某些 CSS 选择器（如 `>>>` 深度选择器），需要用 `/deep/` 或 `::v-deep`
> 2. **API 差异**：微信小程序的 `wx.request` 和支付宝的 `my.request` 参数格式有细微差异，需要封装统一的请求层
> 3. **组件差异**：某些原生组件在不同平台表现不同，比如 `scroll-view` 在微信和支付宝的滚动行为不完全一致
> 4. **条件编译**：`#ifdef MP-WEIXIN` 这种条件编译大量使用，但要注意控制范围，否则代码会变得很难维护
>
> **我的做法：** 封装一层平台适配层，把 API 差异屏蔽在底层，业务代码不感知平台差异。

### 19. 有没有和产品/后端产生过分歧？怎么解决的？

**考察点：** 协作能力、沟通方式

**回答模板：**
> **和产品的分歧：** 做数据大屏时，产品要求"实时刷新，数据一变页面就更新"。我评估后发现如果后端推全量数据、前端全量重绘，大屏会卡顿。我跟产品沟通了技术限制，最终达成方案：后端只推增量数据，前端用增量更新 + requestAnimationFrame 节流，延迟控制在 200ms 内。产品接受了，因为肉眼感知不到这个延迟。
>
> **和后端的分歧：** 工单列表接口一次返回所有数据，前端做分页。我提出应该后端分页，但后端说改动成本大。我的妥协方案是：后端给一个"数据量级"的接口，前端判断数据量 < 5000 就前端分页，> 5000 就要求后端分页。这样既不给后端增加太多工作量，也保证了大数据量场景的性能。

### 20. 你最近读过哪个库的源码？解决了什么问题？

**考察点：** 是否真的有阅读源码的习惯（简历里写了就必须能答）

**回答模板：**

## 七、场景题（开放性问题）

### 21. 如果让你从零搭建一个中型后台管理系统，你会怎么做技术选型？

**考察点：** 架构能力、技术视野

**回答模板：**
> **技术栈：** Vue3 + TypeScript + Vite + Element Plus + Pinia + Vue Router
>
> **关键决策：**
> 1. **TypeScript 必选**：后台管理系统表单多、数据结构复杂，TS 的类型检查能减少大量运行时 bug
> 2. **状态管理选 Pinia**：比 Vuex 更轻量，TS 支持好，API 简洁
> 3. **权限方案**：路由级用 `addRoute` 动态注册，按钮级用自定义指令 `v-permission`
> 4. **请求层**：封装 Axios，统一处理 token 注入、错误拦截、loading 状态
> 5. **构建选 Vite**：开发环境热更新快，HMR 体验好
>
> **工程化：**
> - ESLint + Prettier + Husky 保证代码质量
> - 封装 Layout、Table、Form 等通用组件
> - 路由按模块拆分，支持动态菜单配置
> - CI/CD 自动化部署

### 22. 一个页面加载很慢，你怎么排查？ ⚠️

**考察点：** 问题排查方法论

**回答模板：**
> **按顺序排查：**
>
> 1. **Network 面板看加载情况**：
>    - 有没有特别大的文件（bundle 过大？图片未压缩？）
>    - 有没有串行请求（应该并行的请求被阻塞了？）
>    - TTFB 是否过高（后端响应慢？）
>
> 2. **Performance 面板看渲染情况**：
>    - Long Task 有哪些（JS 执行超过 50ms 的任务）
>    - Layout Shift 是否严重（布局抖动？）
>    - 重排重绘是否频繁
>
> 3. **Lighthouse 跑一次评分**：
>    - 看 LCP / FID / CLS 三个核心指标
>    - 看具体建议（比如"减少未使用的 JS"、"图片用 WebP"）
>
> 4. **内存面板（如果怀疑内存问题）**：
>    - Heap Snapshot 看有没有内存泄漏
>
> **根据排查结果对症下药**，而不是上来就"加懒加载、加缓存"。
